Layered Architecture · Actual Flow

작품 등록을 한 메서드에 몰아넣지 않은 이유

작품 한 건을 등록할 때도 로그인 사용자 확인, 예술관 소유권 검사, 이미지 저장, 태그 연결, 경매 정보 생성까지 함께 움직였습니다. 이 과정을 Controller에 모두 넣으면 수정할 때마다 확인할 범위가 너무 커진다고 판단해 아래처럼 역할을 나눴습니다.

요청 받기WorkAPIController

POST /api/works의 입력과 업로드 파일을 받은 뒤 workService.write()를 호출합니다. 여기서는 요청을 해석하는 일까지만 맡겼습니다.

POST /api/works
입력값 묶기WorkCreateRequestDTO

작품 등록에 실제로 필요한 값만 전달하려고 별도 DTO를 사용했습니다. 조회 응답이나 DB용 객체와 섞이지 않아 필드가 늘어날 때 수정 위치가 분명했습니다.

galleryId · title · files · tags
등록 순서 관리WorkService.write()

작성자와 예술관 권한을 확인한 다음 작품, 파일, 태그, 경매 정보를 순서대로 저장합니다. 중간에 실패하면 DB 작업을 되돌릴 수 있도록 트랜잭션도 이 계층에 두었습니다.

validate → save → link → response
DB 호출 모으기WorkDAO.save()

Service에서 Mapper를 직접 여러 번 호출하지 않도록 저장과 조회 메서드를 DAO에 모았습니다. 덕분에 업무 흐름을 읽을 때 SQL 세부 내용이 끼어들지 않았습니다.

Repository boundary
SQL 실행WorkMapper.insertWork()

실제 INSERT문과 결과 매핑은 Mapper가 담당합니다. 컬럼이나 쿼리를 고칠 때 Java의 등록 순서까지 건드리지 않도록 분리했습니다.

Mapper / SQL
수정 범위를 줄였습니다

요청 형식만 바뀌면 Controller와 DTO를, 쿼리만 바뀌면 Mapper를 먼저 확인하면 됩니다.

오류를 찾기 쉬웠습니다

입력값 문제인지, 권한 검사인지, DB 저장 문제인지 계층 순서대로 좁혀 볼 수 있었습니다.

등록과 조회 DTO를 나눴습니다

등록 화면에 없는 조회 전용 값까지 억지로 한 객체에 담지 않았습니다.
